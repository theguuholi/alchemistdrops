# Elixir Development

Write idiomatic Elixir that preserves immutability, avoids unsafe runtime behavior, and uses focused Mix commands for feedback.

## Language rules

- Access lists with pattern matching, `Enum.at/2`, or `List`; `list[index]` is invalid.
- Bind the result of `if`, `case`, and `cond` when it will be used later. Rebinding only inside the branch does not update the outer binding.
- Prefer one public production module per file; generated code and small test-only helpers may be reasonable exceptions.
- Access struct fields directly. For changesets, use `Ecto.Changeset.get_field/2` rather than Access syntax.
- Never call `String.to_atom/1` on user-controlled input.
- Name predicates with a trailing `?`; reserve `is_` names for guards.
- Prefer the standard `Date`, `Time`, `DateTime`, and `Calendar` APIs before adding a date dependency.

## Module documentation and doctests

- Phoenix LiveView page modules and stateful LiveComponents are framework callback modules, not reusable library APIs. Modules using `use ... :live_view` or `use ... :live_component` do not need `@moduledoc`, `@doc`, ExDoc examples, or doctests; cover their contracts through `@impl` callbacks and focused LiveView tests instead. This exception does not apply to contexts, schemas, presenters, ordinary Elixir modules, or modules that only define function components.
- Give every handwritten production module an ExDoc-compatible `@moduledoc` that explains what the module does, why it exists, and its responsibility in the system. Do not replace meaningful documentation with `@moduledoc false`.
- For context modules such as `Accounts`, explain the domain boundary they own, why that boundary matters, and which operations or invariants callers should access through it.
- Give every public `def` and `defmacro` an ExDoc `@doc` that explains its contract, parameters, return values, and important errors or side effects.
- When the project includes `:ex_doc`, or the user explicitly requests executable documentation, include `iex>` examples for every public name/arity and add `doctest ModuleName` to the corresponding `*_test.exs` module. Without ExDoc, add examples only when they materially clarify the API.
- Keep doctests self-contained and deterministic. Database examples run with `DataCase` and SQL Sandbox; process, time, file, and service examples use supervised or injectable test dependencies rather than production services or uncontrolled global state.
- For side-effecting doctests, assert both the documented return value and the observable effect recorded by the test adapter.
- Private functions cannot receive `@doc`; document their externally observable behavior through the public function that owns it.

## Typespecs

- Do not add `@spec`, `@type`, or `@typedoc` solely for callbacks or helpers inside LiveView page and LiveComponent modules. Keep `@impl true` on behavior callbacks, and move reusable typed APIs into the context, presenter, or another dedicated module.
- Add an accurate `@spec` for every public function and macro, covering every exposed name/arity, including arities generated by default arguments.
- Use `@type`, `@typep`, or `@opaque` for domain values and data structures when the type communicates meaning or is reused across the API. Do not create aliases that only rename a primitive once without adding domain meaning.
- Add `@typedoc` to every public `@type` and `@opaque`, explaining its domain meaning, valid states, and relevant nullability or lifecycle details.
- Context functions must use domain types such as `User.t()` and `Order.t()` instead of generic `struct()` or `map()` whenever the concrete type is known.
- Keep specs aligned with real success/error tuples, `nil` cases, raised exceptions, callbacks, and side effects. Run Dialyzer after changing public types or specs.

## OTP and concurrency

- Give `Registry`, `DynamicSupervisor`, and other named OTP children explicit names in their child specs.
- Place long-lived processes under a supervision tree. Use `Task` for bounded caller-owned work, `Task.Supervisor` when task lifecycle must be supervised independently, and a GenServer only when state or serialized coordination is required.
- Use `Task.async_stream/3` for concurrent enumeration with back-pressure. Choose explicit concurrency and timeout behavior; use `timeout: :infinity` only when the caller can legitimately wait without a deadline.
- In tests, prefer supervised processes and unique names so cases remain isolated.

## Mix workflow

- Run `mix help <task>` before using an unfamiliar task or option.
- Start with the narrowest relevant test file or `mix test --failed`, then run the project's completion check.
- Set `MIX_ENV` deliberately when a task can affect persistent data.
- Treat `mix ecto.drop`, `mix ecto.reset`, rollbacks, and broad dependency cleanup as destructive operations requiring explicit authorization.
- Avoid `mix deps.clean --all` unless dependency artifacts are proven to be the cause.

## Review checklist

- Every production module outside the LiveView page/LiveComponent exception explains its purpose and importance with `@moduledoc`.
- Projects using ExDoc have executable examples for every public function or macro outside that exception, covered by `doctest`.
- Every public function or macro outside that exception has an accurate `@spec`; every public domain type has a meaningful `@typedoc`.
- User input cannot create atoms.
- Block results are bound outside the block.
- Long-lived processes are supervised and test-isolated.
- Concurrent work has deliberate timeout and back-pressure behavior.
- Verification uses the project's documented Mix task.
